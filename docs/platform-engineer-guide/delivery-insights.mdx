# Delivery Insights

:::warning[Alpha]
Delivery Insights is an alpha feature. It is disabled by default and must be opted into, it may contain bugs that become apparent once enabled, and it has not been tested across every OpenChoreo deployment topology. Its API and stored schema may change incompatibly in a later release without notice.
:::

Delivery Insights reports the four DORA metrics — Deployment Frequency, Lead Time for Changes, Change Failure Rate and Mean Time to Recovery — for the components OpenChoreo deploys, at namespace, project or component scope, sliced by environment.

## DORA Metrics

| Metric                    | Answers                                  | Derived from                                           |
| ------------------------- | ---------------------------------------- | ------------------------------------------------------ |
| **Deployment Frequency**  | How often do we ship?                    | Rollouts that reached a healthy state                  |
| **Lead Time for Changes** | How long from commit to running?         | Commit authoring time to rollout ready time            |
| **Change Failure Rate**   | How often does shipping break something? | Failed rollouts, and incidents attributed to a rollout |
| **Mean Time to Recovery** | How long until we are healthy again?     | Incidents, from trigger to resolution                  |

Each metric comes back with its value, a DORA classification (Elite, High, Medium, Low), a trend against the previous window of equal length, and a time-bucketed series at daily, weekly or monthly granularity.

The Observer folds delivery events and incidents into durable facts on a timer, then pre-computes the rollups the API serves. Aggregation runs every five minutes, so a deployment appears in the metrics on the next tick rather than immediately.

## Prerequisites

- An observability plane installed and registered as an `ObservabilityPlane`. See [Observability & Alerting](./observability-alerting.mdx).
- The [observability-logs-opensearch](https://github.com/openchoreo/community-modules/tree/main/observability-logs-opensearch) logs module, version `0.6.0` or later. It is the only logs module that serves the delivery events sweep today.

## Enabling Delivery Insights

Two independent flags, both off by default, and **both are required**. One collects the data; the other shows the page.

### Step 1: Collect the metrics in the Observer

export const deliveryInsightsObserverEnable = `helm upgrade openchoreo-observability-plane ${versions.helmSource}/openchoreo-observability-plane \\
  --version ${versions.helmChart} \\
  --namespace openchoreo-observability-plane \\
  --reuse-values \\
  --set observer.featurePreview.deliveryInsights.enabled=true`;

<CodeBlock language="bash">{deliveryInsightsObserverEnable}</CodeBlock>

The Observer creates its delivery insights tables on startup and begins aggregating. While the flag is off it does not open the store at all, so an installation that never enables the feature carries none of its tables.

### Step 2: Show the page in the portal

export const deliveryInsightsPortalEnable = `helm upgrade openchoreo-control-plane ${versions.helmSource}/openchoreo-control-plane \\
  --version ${versions.helmChart} \\
  --namespace openchoreo-control-plane \\
  --reuse-values \\
  --set backstage.features.deliveryInsights.enabled=true`;

<CodeBlock language="bash">{deliveryInsightsPortalEnable}</CodeBlock>

With this off, **Delivery Insights** is absent from the portal navigation and the page renders a disabled notice if reached by URL.

## Lead Time Needs Commit Provenance

Lead Time for Changes measures from when a commit was **authored** — not when it was committed, built or deployed. OpenChoreo cannot discover that timestamp on its own, so whatever produces the Workload has to record it:

```yaml
spec:
  source:
    commit: <commit SHA, hex, 7 to 40 characters>
    branch: <branch the commit was built from>
    repository: <repository URL>
    authoredAt: <RFC3339 timestamp>
```

Only `commit` and `authoredAt` feed the metric; `branch` and `repository` are provenance for reading a deployment back later. Without them the other three metrics are unaffected, and lead time reports reduced **commit coverage** rather than an estimate.

### Native CI

The built-in workflow templates already do this. The `checkout-source` step resolves the commit and reads its author timestamp:

```bash
COMMIT_AUTHORED_AT=$(git show -s --format=%aI HEAD)
```

and publishes them as the `commit-sha`, `source-branch` and `commit-authored-at` output parameters. The `generate-workload` step passes them to `occ workload create`.

If you write your own CI workflow, wire those outputs through to `generate-workload` the way the shipped builders do:

```yaml
- name: generate-workload
  arguments:
    parameters:
      - name: source-commit
        value: "{{steps.checkout-source.outputs.parameters.commit-sha}}"
      - name: source-branch
        value: "{{steps.checkout-source.outputs.parameters.source-branch}}"
      - name: source-repository
        value: "{{workflow.parameters.git-repo}}"
      - name: source-authored-at
        value: "{{steps.checkout-source.outputs.parameters.commit-authored-at}}"
```

A workflow that leaves these out still builds and deploys. It just produces Workloads with no provenance, and those deployments count towards every metric except lead time.

### External CI

A pipeline outside OpenChoreo passes the same four values as flags on `occ workload create`:

```bash
occ workload create \
  --namespace acme-corp \
  --project online-store \
  --component product-catalog \
  --descriptor workload.yaml \
  --image "$IMAGE" \
  --source-commit "$(git rev-parse HEAD)" \
  --source-branch "$BRANCH" \
  --source-repository https://github.com/my-org/my-repo \
  --source-authored-at "$(git show -s --format=%aI HEAD)"
```

Run it in the checked-out repository, at the commit the image was built from — both `git` commands read the working tree rather than anything OpenChoreo provides.

Three things to get right:

- **Use the author date, `%aI`.** Not the committer date (`%cI`), which a rebase rewrites, and not the build time, which would make every deployment look instantaneous.
- **`--source-authored-at` must be RFC3339.** `git show -s --format=%aI` produces exactly that.
- **`--source-commit` must be a SHA.** It is validated as 7 to 40 hex characters, so a branch or tag name is rejected rather than stored as provenance pointing at nothing. A short SHA is accepted; native CI records the full 40.

## Access

Reading the metrics requires the `deliveryinsights:view` action. The portal, the read API and the MCP tools all enforce it. By default it is granted by the `admin`, `platform-engineer`, `developer` and `sre` roles.

## Querying from an Agent

The observability plane MCP server exposes the metrics as two tools, so an agent can answer delivery questions without going through the portal. Both are served from the Observer's `/mcp` endpoint and enforce the same `deliveryinsights:view` action as the portal.

| Tool                     | Returns                                                                                                           |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| `query_dora_metrics`     | The four metrics for a scope and window: value, classification, trend and a time-bucketed series                  |
| `query_dora_deployments` | The individual rollouts behind those numbers, with project, component, environment, commit, outcome and lead time |

Both require `namespace`, `start_time` and `end_time`, and narrow with `project`, `component` and `environment`. `query_dora_metrics` also takes `granularity` and a `metrics` list to compute a subset; `query_dora_deployments` takes `limit` and `sort_order`.

Classification depends on the length of the window. The same rollouts can read `Elite` over a week and `High` over a month, because the per-day rate falls as the window widens. Compare like windows.

See [MCP Servers](../reference/mcp-servers.mdx) for connecting an assistant to the observability plane.

| Value                                              | Default | Description                                                                   |

| Value                                         | Default | Description                                                                              |
