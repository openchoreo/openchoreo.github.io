# Maintain a Provisioned Resource

Creating a Resource is only the start. Maintaining it, often called day 2 operations, means giving
the database more CPU, growing its storage, tuning it and upgrading it. This tutorial makes each of
those changes to a PostgreSQL database that OpenChoreo provisions through Crossplane on AWS, Azure or
GCP, and shows where each change goes and what it does to the running database.

## Overview

A Resource can change in two places, and which one you use decides how the change reaches each
environment:

| Change                                                              | Where you make it                                                                                                                                   | How it reaches an environment                                                                                                                        |
| :------------------------------------------------------------------ | :-------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------- |
| The same in every environment, such as the PostgreSQL major version | The Resource, under `spec.parameters`                                                                                                               | OpenChoreo cuts a new [ResourceRelease](../reference/api/runtime/resourcerelease.md). Each environment moves to it only when you promote its binding |
| Different per environment, such as size or storage                  | The [ResourceReleaseBinding](../reference/api/platform/resourcereleasebinding.md) for that environment, under `spec.resourceTypeEnvironmentConfigs` | Applies to that environment straight away, without a new release                                                                                     |

So a version upgrade reaches development first and production only when you promote it there, while
scaling production up does not touch development at all.

The ResourceType decides which settings exist. It is the same on every cloud, and so is every command
in this tutorial. What a change does to the running database, and how long it takes, is decided by
the backing on the data plane: Amazon RDS for PostgreSQL, Azure Database for PostgreSQL flexible
server or Cloud SQL for PostgreSQL. Each step ends with what the change did on each of them. Pick your
cloud in one of those tabs and the rest of the page follows. The timings were measured in testing, and
vary with region and size.

## Prerequisites

Before you begin, ensure you have:

- **OpenChoreo installed**, with the `development` environment (the default installation has
  `development`, `staging` and `production`)
- **[occ CLI](../getting-started/cli-installation.mdx)** installed and configured for your OpenChoreo installation
- **kubectl** configured to access your cluster
- **The [Crossplane provisioner module](https://github.com/openchoreo/community-modules/tree/main/provisioner-crossplane)**
  installed, with the backing for your cloud on the data plane and the `postgres-crossplane-advanced`
  ClusterResourceType on the control plane. Follow the module README, then the "PostgreSQL (advanced)"
  section of the guide for your cloud:
  [AWS](https://github.com/openchoreo/community-modules/tree/main/provisioner-crossplane/aws#postgresql-advanced),
  [Azure](https://github.com/openchoreo/community-modules/tree/main/provisioner-crossplane/azure#postgresql-advanced)
  or [GCP](https://github.com/openchoreo/community-modules/tree/main/provisioner-crossplane/gcp#postgresql-advanced).

:::warning Cost
This tutorial creates a real managed PostgreSQL database in your cloud account. Delete it when you are
done, as described in [Clean Up](#clean-up).
:::

:::tip If your cloud rejects a size
Each size maps to a machine size that the backing picks: an instance class on AWS, a SKU on Azure and a
machine type on GCP. If it is not offered in your region or account, point the size at one that is with
`postgres.sizes` in the data plane's EnvironmentConfig, for example `small: {instanceClass: db.t4g.medium}`
on AWS, `small: {sku: GP_Standard_D2ds_v5}` on Azure or `small: {tier: db-custom-2-7680}` on GCP. Azure
in particular can refuse a SKU with `SkuNotAvailable` even when its capability list offers it, most
often with Burstable SKUs. The change applies to new and existing databases without touching any
Resource.
:::

## Step 1 — Create the Resource

Create a PostgreSQL Resource in the `default` project. Its parameters apply to every environment.

```bash
occ apply -f - <<EOF
apiVersion: openchoreo.dev/v1alpha1
kind: Resource
metadata:
  name: orders-db
  namespace: default
spec:
  owner:
    projectName: default
  type:
    kind: ClusterResourceType
    name: postgres-crossplane-advanced
  parameters:
    database: orders
    version: "16"
    extensions: [vector]
EOF
```

OpenChoreo cuts a ResourceRelease from the Resource. Nothing is provisioned yet, because no
environment is bound to it.

```bash
occ resource get orders-db -n default
```

The `latestRelease` in the output names the release.

## Step 2 — Bind It to Development

Create the binding for `development`. Its `resourceTypeEnvironmentConfigs` hold the settings for that
environment only. Start small, with 64 GiB of storage:

```bash
occ apply -f - <<EOF
apiVersion: openchoreo.dev/v1alpha1
kind: ResourceReleaseBinding
metadata:
  name: orders-db-development
  namespace: default
spec:
  owner:
    projectName: default
    resourceName: orders-db
  environment: development
  resourceTypeEnvironmentConfigs:
    capacity:
      size: small
      storageGb: 64
EOF
```

Each size comes with a default amount of storage. Setting `storageGb` keeps storage where it is when
the size changes, so the size and storage changes below stay separate. That matters on AWS, where RDS
accepts only one storage change every six hours.

The binding waits until it is pinned to a release. Promote it to the latest one:

```bash
occ resource promote orders-db --env development -n default
```

Creating the database takes about ten minutes on each cloud. Wait for the binding to become Ready:

```bash
kubectl wait rrb orders-db-development -n default --for=condition=Ready --timeout=30m
```

Then look at its outputs:

```bash
occ resourcereleasebinding get orders-db-development -n default
```

The outputs are `host`, `port`, `database`, `username` and `password`. `password` is a reference to a
Secret on the data plane, `<name>-conn`, so the password itself never reaches the control plane.
A Workload uses them through a [resource dependency](../developer-guide/dependencies/resources.md).

The rest of this tutorial changes the binding with `kubectl patch`. Each patch merges into the
settings already on the binding.

## Step 3 — Scale CPU and Memory

Move development from `small` to `medium`:

```bash
kubectl patch rrb orders-db-development -n default --type merge \
  -p '{"spec":{"resourceTypeEnvironmentConfigs":{"capacity":{"size":"medium"}}}}'
```

Each size maps to a machine size on the cloud, so this changes it, and the database restarts:
**connections are refused for part of the change**. Parameters you set yourself keep their values.

<Tabs groupId="cloud">
<TabItem value="aws" label="AWS">

The instance class changed in about three and a half minutes. Connections were refused for about two
minutes, then for about ten seconds more in a second restart.

</TabItem>
<TabItem value="azure" label="Azure">

The SKU changed in about ten minutes, and connections were refused for about 20 seconds. Server
parameters that Azure sizes from memory, such as `shared_buffers`, followed the new SKU.

</TabItem>
<TabItem value="gcp" label="GCP">

The machine type changed in about five minutes, and connections were refused for 15 to 20 seconds.
Flags that Cloud SQL sizes from memory, such as `shared_buffers`, followed the new machine type.

</TabItem>
</Tabs>

Lowering the size works the same way. Storage stays as it is: it never shrinks, even where `storageGb`
is not set and the smaller size has less storage by default.

## Step 4 — Grow Storage

Grow storage to 128 GiB and let the cloud grow it further when it runs low:

```bash
kubectl patch rrb orders-db-development -n default --type merge \
  -p '{"spec":{"resourceTypeEnvironmentConfigs":{"capacity":{"storageGb":128,"storageAutoGrow":true}}}}'
```

Storage grows online, **with no restart**.

<Tabs groupId="cloud">
<TabItem value="aws" label="AWS">

Growing from 32 to 64 GiB took about four and a half minutes in testing. RDS then optimizes the
storage, which took about another 14 minutes, and refuses another storage change for six hours or
until the optimization ends, whichever is longer. Automatic growth goes up to 1024 GiB, unless the data
plane sets `postgres.storageAutoGrowLimitGb`.

</TabItem>
<TabItem value="azure" label="Azure">

Growing from 64 to 128 GiB took about three and a half minutes.

</TabItem>
<TabItem value="gcp" label="GCP">

Growing from 32 to 64 GiB took under a minute in testing, and turning on automatic growth took about
half a minute.

</TabItem>
</Tabs>

Storage cannot shrink. Try it:

```bash
kubectl patch rrb orders-db-development -n default --type merge \
  -p '{"spec":{"resourceTypeEnvironmentConfigs":{"capacity":{"storageGb":64}}}}'
```

The change is rejected on the data plane before anything reaches the cloud, and the binding reports
`storage can grow but not shrink`. Set it back to 128 to clear the error.

## Step 5 — Tune Server Parameters

Each setting under `configuration` is one PostgreSQL parameter:

```bash
kubectl patch rrb orders-db-development -n default --type merge -p '{
  "spec": {"resourceTypeEnvironmentConfigs": {"configuration": {
    "memory":   {"workMemMb": 16, "maintenanceWorkMemMb": 128},
    "timeouts": {"statementTimeoutSeconds": 30, "idleInTransactionTimeoutSeconds": 60, "lockTimeoutSeconds": 10},
    "logging":  {"slowQueryThresholdMs": 500, "logStatement": "ddl", "queryStats": "top"}
  }}}}'
```

These apply **live, with no restart**, and removing a setting resets it to the cloud's default. Each
cloud supports most of them, but not all:

<Tabs groupId="cloud">
<TabItem value="aws" label="AWS">

`timeouts.lockTimeoutSeconds` is not used: `lock_timeout` is not an RDS parameter, and RDS rejects
the whole update if any parameter is unknown. Set it per database instead, with
`ALTER DATABASE orders SET lock_timeout = '10s'`. The other seven went into the instance's parameter
group in one update, and applied about ten seconds after the binding changed.

</TabItem>
<TabItem value="azure" label="Azure">

Azure applies them one at a time, about 20 seconds each, so these eight took about two minutes.

Azure also runs one operation on a server at a time. If you change the size, storage or maintenance
window while server parameters are still being applied, Azure answers `ServerIsBusy`. Crossplane
retries, but only on its next poll, which can be up to ten minutes later, so changes go through faster
in separate steps.

</TabItem>
<TabItem value="gcp" label="GCP">

`timeouts.statementTimeoutSeconds` is not used: `statement_timeout` is not a Cloud SQL flag, and Cloud
SQL rejects the whole update if any flag is unsupported. Set it per database instead, with
`ALTER DATABASE orders SET statement_timeout = '30s'`. The other seven went in one update, which took
12 seconds.

</TabItem>
</Tabs>

`connections.maxConnections` is the exception. PostgreSQL only reads `max_connections` at startup, so
a new value needs a restart:

<Tabs groupId="cloud">
<TabItem value="aws" label="AWS">

RDS stores the value and reports it as `pending-reboot`, but does not restart for it. It applies at the
instance's next restart, such as a size change, or when you reboot the instance yourself. The reboot
refused connections for under ten seconds.

</TabItem>
<TabItem value="azure" label="Azure">

The server restarts **straight away, outside the maintenance window**. The restart took about a
minute.

</TabItem>
<TabItem value="gcp" label="GCP">

Cloud SQL restarts the instance **straight away, outside the maintenance window**. Connections were
refused for 5 to 10 seconds.

</TabItem>
</Tabs>

## Step 6 — Set the Maintenance Window and Network Access

The cloud applies minor versions and patches on its own schedule. Pin them to a weekly window, in
UTC, and allow one more network to connect:

```bash
kubectl patch rrb orders-db-development -n default --type merge -p '{
  "spec": {"resourceTypeEnvironmentConfigs": {
    "maintenance": {"window": {"dayOfWeek": 0, "startHour": 2}},
    "network": {"firewallRules": [
      {"name": "office", "startIpAddress": "203.0.113.10", "endIpAddress": "203.0.113.10"}
    ]}
  }}}'
```

Neither change restarts the database. The rule is added next to the rules the data plane already
has, and removing it from the list deletes it. A rule that would admit every address is rejected.

<Tabs groupId="cloud">
<TabItem value="aws" label="AWS">

The window applied in about ten seconds. The rule becomes an ingress rule in the instance's own
security group, and an address could connect three seconds after its rule was added. The instance
has no public endpoint, so a rule only helps addresses that reach the VPC, such as peered VPCs or
networks connected by VPN or Direct Connect. An office on the internet, like the one above, cannot
connect.

</TabItem>
<TabItem value="azure" label="Azure">

The rule becomes a server firewall rule named `env-office`. Each change took a few minutes.

</TabItem>
<TabItem value="gcp" label="GCP">

Both went in one update, which took 22 seconds. Cloud SQL starts a window on the hour, so
`startMinute` is not used. The rule becomes an authorized network on a public IP, which the instance
has only while the environment lists rules. Workloads keep using the private IP in `host`. Removing
the last rule turned the public IP off in about a minute and a half.

</TabItem>
</Tabs>

## Step 7 — Upgrade the Major Version, One Environment at a Time

The major version is a parameter, so it lives on the Resource and goes through a release. Raise it to
17:

```bash
kubectl patch resource orders-db -n default --type merge \
  -p '{"spec":{"parameters":{"version":"17"}}}'
```

OpenChoreo cuts a new ResourceRelease, but **no environment moves yet**. `development` stays on the
old release until you promote it:

```bash
occ resource promote orders-db --env development -n default
```

The cloud upgrades the database in place, and **connections are refused for part of the upgrade**.
Parameters and extensions carry over.

<Tabs groupId="cloud">
<TabItem value="aws" label="AWS">

From 16 to 17 took about six minutes, with about two minutes of refused connections. The instance
answered as version 17 about three and a half minutes after the promotion, and moved to a parameter
group for 17 in the same change. Automated backups are off in every size, so RDS takes no snapshot
before the upgrade. Take one yourself if the data matters.

</TabItem>
<TabItem value="azure" label="Azure">

From 16 to 17, the server answered as version 17 after about four minutes, and connections were
refused for about a minute of that time. Azure went on reporting the upgrade as in progress for about
19 minutes.

</TabItem>
<TabItem value="gcp" label="GCP">

From 16 to 17 took about fourteen and a half minutes. Cloud SQL backed the instance up before and
after the upgrade, and refused connections for about four and a half minutes in between. The instance
answered as version 17 about nine minutes after the promotion.

</TabItem>
</Tabs>

If the Resource is also bound to `staging`, move staging to the release that development runs once
development looks good. `occ resource promote` always takes the latest release, which is not the one
development tested if the Resource changed in the meantime, so pin the release by name:

```bash
release=$(kubectl get rrb orders-db-development -n default -o jsonpath='{.spec.resourceRelease}')
kubectl patch rrb orders-db-staging -n default --type merge \
  -p "{\"spec\":{\"resourceRelease\":\"$release\"}}"
```

The version cannot go down. Setting it back to 16 cuts a release, but a binding promoted to it reports
`version can be raised but not lowered`, and nothing reaches the cloud.

## Clean Up

Delete the binding. The ResourceType's `retainPolicy` is `Delete`, so Crossplane deletes the database
in your cloud:

```bash
kubectl delete rrb orders-db-development -n default
kubectl delete resource orders-db -n default
```

## Summary

- A change on the **Resource** cuts a release and reaches each environment only when you promote its
  binding. Use it for what must match everywhere, such as the major version.
- A change on the **ResourceReleaseBinding** applies to that environment straight away. Use it for
  what differs per environment, such as size, storage and tuning.
- The commands are the same on every cloud, but what a change does to the database is up to the
  backing. A `max_connections` change restarts the database at once on Azure and GCP, and waits for
  the next restart on AWS. Check your cloud's guide before changing production.
